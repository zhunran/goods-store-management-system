## 一、系统概述

### 1.1 系统定位

基于 Spring Cloud 微服务架构的并发商城系统，支持商品浏览、购物车、订单交易、秒杀抢购、会员管理、权限控制等核心电商功能。

### 1.2 核心业务闭环

```
商品管理 → 会员浏览 → 购物车 → 下单 → 支付 → 订单管理 → 售后
                                    ↓
                              秒杀抢购（高并发场景）
```

### 1.3 微服务模块划分

| 服务名称                | 端口 | 职责                             | 对应数据表                       |
| ----------------------- | ---- | -------------------------------- | -------------------------------- |
| goods-store-gateway     | 8080 | 网关：JWT 校验 + 路由 + 限流     | -                                |
| goods-store-auth-api    | 8081 | 认证服务：登录、注册、Token 管理 | member, auth\_\*                 |
| goods-store-brand-api   | 8082 | 品牌服务：品牌 CRUD              | brand                            |
| goods-store-product-api | 8083 | 商品服务：分类、商品、详情图     | category, good, good_detail_pics |
| goods-store-member-api  | 8084 | 会员服务：会员信息、收货地址     | member, member_address           |
| goods-store-trade-api   | 8085 | 交易服务：购物车、订单、订单明细 | cart, order, order_detail        |
| goods-store-seckill-api | 8086 | 秒杀服务：秒杀商品、秒杀订单     | seckill_good, seckill_order      |

## 二、模块与功能设计

### 2.1 认证服务（goods-store-auth-api）

#### 2.1.1 功能列表

| 功能编号 | 功能名称   | 优先级 | 说明                                        |
| -------- | ---------- | ------ | ------------------------------------------- |
| AUTH-001 | 会员注册   | P0     | 手机号/邮箱注册，BCrypt 密码加密            |
| AUTH-002 | 会员登录   | P0     | JWT 双 Token 签发（Access + Refresh）       |
| AUTH-003 | Token 刷新 | P0     | Refresh Token 换取新 Access Token           |
| AUTH-004 | 登出       | P0     | Access Token 加入黑名单，Refresh Token 删除 |
| AUTH-005 | 密码修改   | P1     | 旧密码验证 + 新密码 BCrypt 加密             |
| AUTH-006 | 密码重置   | P1     | 短信/邮箱验证码重置                         |

#### 2.1.2 关联数据表

| 表名                 | 用途                                      |
| -------------------- | ----------------------------------------- |
| member               | 会员基本信息，account + password 用于登录 |
| auth_user            | 后台管理员用户                            |
| auth_role            | 角色定义                                  |
| auth_permission      | 权限定义                                  |
| auth_user_role       | 用户-角色关联                             |
| auth_role_permission | 角色-权限关联                             |

#### 2.1.3 关键设计决策

- **双 Token 机制**：Access Token 短效（30min），Refresh Token 长效（7天），存 Redis 支持服务端吊销
- **密码加密**：BCrypt，与你的物业系统一致
- **权限模型**：RBAC（用户-角色-权限），支持后台管理员多级权限

| 表名          | 用途                                         |
| ------------- | -------------------------------------------- |
| seckill_good  | 秒杀商品（关联 good 表，独立秒杀价格和库存） |
| seckill_order | 秒杀订单（关联 member + seckill_good）       |

#### 2.6.3 秒杀并发控制（核心设计）

| 防护层                     | 实现方式                                                | 说明                     |
| -------------------------- | ------------------------------------------------------- | ------------------------ |
| **第一层：Redis 预减库存** | 秒杀开始前将库存预热到 Redis，抢购时先原子减 Redis 库存 | 减少数据库压力           |
| **第二层：消息队列削峰**   | 秒杀请求先入 MQ，异步处理订单生成                       | 避免瞬时高并发打垮数据库 |
| **第三层：数据库乐观锁**   | 更新秒杀库存时用 `WHERE stock > 0` 兜底                 | 防止超卖                 |
| **第四层：限流**           | 网关层 + 服务层双层限流，防止恶意刷单                   | 保护系统                 |

#### 2.6.4 接口设计

| 接口         | 方法 | 路径                    | 说明           |
| ------------ | ---- | ----------------------- | -------------- |
| 秒杀商品列表 | GET  | /api/seckill/list       | 当前可秒杀商品 |
| 秒杀商品详情 | GET  | /api/seckill/{id}       | 秒杀商品详情   |
| 秒杀抢购     | POST | /api/seckill/{id}/order | 秒杀下单       |

## 六、关键设计决策总结

| 决策           | 选择                                     | 原因                                                |
| -------------- | ---------------------------------------- | --------------------------------------------------- |
| 微服务拆分粒度 | 7 个服务                                 | 按业务域拆分，避免过度拆分增加运维成本              |
| SPI 层         | 合并为一个模块                           | 每个 SPI 只有 1-2 个 Feign 接口，独立模块维护成本高 |
| 鉴权方案       | JWT 双 Token + 网关校验                  | 与物业系统一致，复用经验                            |
| 秒杀并发       | Redis 预减库存 + MQ 削峰 + 乐观锁 + 限流 | 四层防护，与物业系统支付回调思路一致                |
| 订单状态机     | PENDING → PAID → SHIPPED → COMPLETED     | 清晰的状态流转，支持取消和退款                      |
| 跨服务调用     | Feign + SPI 契约                         | 服务间调用只需依赖 SPI 包，不引入完整 Service       |
