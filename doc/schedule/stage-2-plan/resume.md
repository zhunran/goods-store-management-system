## 二、逐日审阅

### Day 1-2：基础设施搭建 ✅ 可行，但有两个调整建议

**亮点：**

- Nacos 共享配置 + 父 POM 版本管理，减少重复配置
- 雪花算法提前封装，后续服务直接使用
- MQ 消息体 DTO 提前定义，避免后期接口不一致

**风险点与调整建议：**

| 风险                                           | 建议                                                                                                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Nacos 共享配置与各服务本地配置的优先级**     | 在 `goods-store-common.yaml` 中明确标注：`shared-configs` 的 `refresh` 设为 `true`，支持热更新                                                                 |
| **Druid 数据源配置中开启了 Wall 防火墙**       | Wall 过滤器可能拦截多表 JOIN 或子查询，建议在 `wall` 配置中添加 `multi-statement-allow: true` 和 `none-base-statement-allow: true`，避免后续商品查询时被误拦截 |
| **网关限流用了 Guava RateLimiter（单机限流）** | 这是单体网关的限流，如果网关部署多实例，需要换成 Redis 分布式限流。建议在计划中备注"当前为单机限流，后续可升级为 Redis 令牌桶"                                 |

**补充验收标准：**

- [ ] Nacos 控制台修改配置后，服务能动态刷新（验证 `@RefreshScope` 生效）

### Day 3-4：认证服务 ✅ 可行，但 RBAC 权限模型需要明确边界

**亮点：**

- JWT 双 Token + Redis 黑名单，与你的物业系统完全一致，可复用经验
- 权限模型用 RBAC（用户-角色-权限），标准且可扩展

**风险点与调整建议：**

| 风险                                   | 建议                                                                                                                                                                                                                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **RBAC 权限模型在"并发商城"中的定位**  | 商城系统的权限分两类：**后台管理权限**（管理员、运营、客服）和**前端会员权限**（普通用户、VIP）。计划中只提到了 RBAC，但没有区分这两类权限。建议在 Day 3 任务中明确：auth-api 同时管理后台管理员和前端会员的认证，但 RBAC 只用于后台管理员，前端会员用简单的"角色字段"区分 |
| **Refresh Token 存 Redis 的 key 设计** | 建议在计划中明确 key 格式：`token:refresh:{userId}:{role}`，与你的物业系统保持一致                                                                                                                                                                                         |

**补充验收标准：**

- [ ] 管理员登录后，不同角色（超级管理员/普通管理员）访问不同接口，权限控制生效
- [ ] Refresh Token 过期后，刷新接口返回 401

### Day 9-11：交易服务 ⚠️ 任务量偏重，需要拆分或延长

**亮点：**

- 购物车 + 下单 + MQ + 超时取消，完整闭环
- 订单状态机设计清晰

**风险点与调整建议：**

| 风险                                                   | 建议                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Day 9-11 三天任务量明显偏重**                        | 购物车（CRUD + 唯一约束）、下单（库存扣减 + Feign 调用商品服务 + MQ 异步）、MQ 消息（发送 + 消费 + 手动确认 + 死信队列）、超时取消（死信队列 + 幂等处理），这四个模块加起来工作量很大。建议：**Day 9-10 完成购物车 + 下单（不含 MQ），Day 11 单独做 MQ + 超时取消**，如果时间不够，超时取消可延后到 Day 12 |
| **下单时跨服务调用商品服务扣库存，但库存扣减是同步的** | 如果商品服务响应慢，下单接口会被拖慢。建议在计划中备注：当前为同步扣库存，后续可优化为"Redis 预扣库存 + MQ 异步扣减"                                                                                                                                                                                       |
| **MQ 消息可靠性**                                      | 计划中提到了"手动确认 + 死信队列"，但缺少"消息幂等"的验收标准。建议补充：同一条订单创建消息重复消费，不会重复创建订单                                                                                                                                                                                      |

**补充验收标准：**

- [ ] 同一条订单创建消息消费两次，只创建一条订单（幂等验证）
- [ ] 死信队列消费后，订单状态正确更新为"已取消"

## 三、全局风险点

| 风险                   | 影响                                                   | 建议                                                                                                 |
| ---------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| **Nacos 服务注册延迟** | 服务启动后，网关可能路由到未就绪的服务                 | 在网关配置中开启 `spring.cloud.gateway.discovery.locator.enabled`，并配置 `readiness-state` 健康检查 |
| **Feign 超时与重试**   | 跨服务调用超时，可能导致下单失败                       | 在 Feign 配置中设置 `connect-timeout: 3000`、`read-timeout: 5000`，并配置重试次数（默认 1 次）       |
| **MQ 消息堆积**        | 秒杀场景下 MQ 消息量暴增，消费速度跟不上               | 在 Day 12-13 中补充：MQ 消费者线程池配置，支持动态扩容消费者实例                                     |
| **数据库连接池耗尽**   | 多个服务连接同一个数据库，总连接数可能超限             | 在 Nacos 共享配置中，把 Druid `max-active` 从 20 降到 10，每个服务单独配置，避免总连接数超限         |
| **Redis 内存不足**     | 秒杀库存 + Token 黑名单 + 缓存数据，Redis 内存可能不够 | 在 Day 1 中补充 Redis 内存配置：`maxmemory 256mb`，`maxmemory-policy allkeys-lru`                    |

## 五、最终结论

**计划可行，但建议做以下调整：**

1. **Day 9-11 交易服务**：拆分为 Day 9-10（购物车 + 下单）和 Day 11（MQ + 超时取消），如果时间不够，超时取消延后到 Day 12
2. **Day 12-13 秒杀服务**：补充并发测试验收标准（1000 并发不超卖）
3. **Day 14 集成测试**：拆成 3 条具体链路（正常下单、秒杀、服务降级）
4. **全局补充**：Feign 超时配置、MQ 幂等验证、Redis 内存配置、数据库连接池配置

**如果按这个计划执行，14 天完成一个可用的并发商城系统是可行的，而且你的物业管理系统经验可以直接复用，效率会比纯新手高很多。**
