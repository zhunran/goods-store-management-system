## 一、业务全景

**一句话定位**：面向消费者的 B2C 电商平台（主营 3C 数码电子）+ 面向运营方的后台管理系统，覆盖「逛 → 选 → 买 → 抢 → 履约」的完整交易闭环。

### 用户旅程（C 端 / B 端双视角）

| 旅程环节 | C 端用户（owner-web）                     | B 端运营（admin-web）                       |
| -------- | ----------------------------------------- | ------------------------------------------- |
| 逛       | 首页推荐、品牌街、分类树、商品列表 / 详情 | 品牌 / 商品 / 分类 / SKU / 规格管理、上下架 |
| 买       | 加购、购物车、收货地址、结算下单          | 订单查询、状态流转、会员管理                |
| 抢       | 秒杀场次倒计时、抢购、结果轮询            | 秒杀活动配置、库存预热                      |
| 保障     | 登录无感续期、订单查询 / 取消、资料维护   | 会员敏感信息脱敏展示、RBAC 权限             |

### 支撑底座

- 6 大业务域微服务（认证 / 品牌 / 商品 / 会员 / 交易 / 秒杀）+ 网关统一鉴权限流 + BFF 聚合层（前端唯一入口 `/app/api/**`）
- 中间件：Nacos（注册 + 配置）、MySQL、Redis + Redisson（缓存 / 分布式锁 / 秒杀库存）、RabbitMQ（异步解耦）
- 可观测性：SkyWalking 8 服务全量链路追踪
- 前端双端：owner-web（用户端，蓝白电子专卖风格）+ admin-web（管理端）

## 二、核心业务链路

### 1. 日常购物下单（交易主链路）

```
结算下单 → 订单服务（事务内：校验商品存在 / 库存充足、取默认收货地址、
           落库订单 + 订单项）
  ├─ 事务提交后发两条 MQ 消息：
  │   ① order.create  → 异步扣减商品 DB 库存
  │   ② order.timeout → 30 分钟延迟队列 → 死信转取消链路，未支付订单自动关单并恢复库存
  └─ 清空购物车 → 返回订单号与应付金额
```

业务保障点：

- **防重复下单**：Redisson 分布式锁按会员维度加锁（等待 10s / 租期 30s），拦截连点与并发重复提交；释放前校验 `isHeldByCurrentThread`，避免误删他人锁
- **防超卖（DB 层兜底）**：扣减 SQL 为 `UPDATE good SET qty = qty - #{count} WHERE id = #{goodId} AND qty >= #{count}`，库存不足则不生效，负数库存不可能出现
- **消息与事务一致性**：MQ 消息在**事务提交后**（afterCommit）才发出，杜绝「消息已发、事务回滚」的脏消息

### 2. 秒杀抢购（高并发链路）

```
点击抢购 → 三道闸门（同步毫秒级返回「排队中」）：
  ① Redis Lua 脚本原子执行：查库存 → 限购防重 → 预扣减，一次网络往返完成
  ② 库存键缺失时自动回源：查 DB → setnx 幂等回写 Redis（不覆盖已扣减值）→ 重试一次
  ③ RabbitMQ 异步建单：消费者幂等校验后落库
前端按订单号轮询结果 → 排队中 / 已抢到
```

业务保障点：

- **原子性**：Lua 脚本内「判断库存 + setnx 防重 + 扣减」原子执行，无竞态窗口；返回值区分售罄 / 已参与 / 键不存在
- **限购**：每人每件限购 1 件（`seckill:order:{memberId}:{seckillGoodId}` setnx 防重键）
- **削峰**：DB 完全不承压——秒杀扣减只发生在 Redis，订单由 MQ 消费者异步落库
- **预热**：定时任务每分钟扫描「5 分钟内开抢 + 进行中」的活动，将 DB 库存 setnx 写入 Redis，活动结束后键自动过期（结束时间 + 1 小时）
- **失败补偿**：消费者异常时回滚 Redis 库存、清除防重键后 ack（不无限重试，防消息毒丸堆积）

### 3. 账号与会话

- **双令牌**：access token 30 分钟 + refresh token 7 天，过期前静默续期，用户无感知
- **登录防爆破**：同账号连续失败 3 次锁定 15 分钟（Redis 计数）
- **登出即刻失效**：access token 入 Redis 黑名单；网关校验时**精确比对 token 全文**，重新登录签发的新 token 不被旧黑名单误杀
- **数据合规**：手机号脱敏为 `138****5678`、身份证前 4 后 4 位；服务间内部接口不脱敏，对前端出口统一脱敏

## 三、项目亮点

每条按「业务问题 → 方案 → 业务价值」组织。

### 亮点 1：秒杀「三道闸门」体系——不超卖、不少卖、页面不卡

- **问题**：瞬时高并发下，直接打 DB 会被打穿；先查后扣存在超卖竞态；失败请求需要正确回滚
- **方案**：Redis Lua 原子预扣（判断 + 防重 + 扣减一次往返）→ MQ 异步建单削峰 → 消费失败自动补偿回滚库存
- **价值**：同步链路毫秒级返回、DB 零压力；Lua 原子性从根上消除竞态；限购防重抑制黄牛刷单；缓存键缺失可自动回源预热，具备故障自愈能力

### 亮点 2：订单最终一致性——异步化的同时不丢账

- **问题**：异步扣库存 + 延迟关单引入一致性问题：消息与事务、订单与库存、超时与恢复三对关系
- **方案**：事务提交后才发消息；扣减 SQL 带库存充足条件；30 分钟 TTL 延迟队列 + 死信自动触发取消并恢复库存；消费端按订单号幂等
- **价值**：用户视角「下单即响应、超时自动关、库存零负数」，运营视角无需人工对账干预

### 亮点 3：账号安全三件套 + 数据合规

- 双令牌无感续期（30min / 7d）、登录失败锁定（3 次 / 15 分钟）、登出黑名单精确比对（新会话不误杀）
- JWT 密钥经环境变量 `JWT_SECRET` 注入（带固定默认值），网关与 auth-api 一致且服务重启不漂移：即使停服重启、Redis 未清，refresh token 仍可静默续期，用户无需重新登录
- 管理端会员列表 / 详情的手机号、身份证出口强制脱敏，内部调用保持明文
- 网关统一鉴权（GlobalFilter 优先级 -100）+ RBAC 五表权限模型 + 密码 BCrypt 加密

### 亮点 4：全链路可观测

- SkyWalking Agent + OAP + UI，8 个服务零代码侵入全量接入
- 实测：跨服务 Trace 单链 4 服务 46 Span（sw8 头透传）、SQL 观测（MyBatis / JDBC / Druid）、错误追踪含异常堆栈事件
- 业务价值：一次请求跨网关 → BFF → 多个微服务 → MQ 消费者的完整路径可回放，排障从「翻多服务日志」变为「看一条链路」

### 亮点 5：微服务工程化治理

- **SPI 契约层**：服务间只依赖接口契约（goods-store-spi），不依赖彼此实现
- **降级容错**：product → brand 的 Feign 调用带 FallbackFactory，品牌服务抖动不影响商品展示
- **上下文透传**：网关解析 JWT 后以 `X-User-Id` / `X-User-Roles` 下发，Feign 拦截器继续透传，下游服务无状态
- **链路标识**：TraceId 贯穿 Web → Feign → MQ，跨服务日志可串联
- **分布式主键**：雪花算法，7 个服务分配不同 worker-id（1~7）

### 亮点 6：双端前端完整交付

- owner-web（用户端）：首页 / 登录注册 / 商品列表详情 / 秒杀 / 购物车 / 结算 / 订单 / 个人中心，蓝白电子专卖风格（锐利圆角体系），类型检查 + 生产构建通过
- admin-web（管理端）：登录、仪表盘、品牌、商品、会员、订单、秒杀页面
- 前端统一走网关 → BFF 的 `/app/api/**` 单一入口，开发期 Vite proxy 转发

### 亮点 7：前沿技术栈的工程落地

- Java 25 + Spring Boot 4.1 + Spring Cloud 2025.1 + SCA 2025.1 + Jackson 3，均为当前最新世代组合，完整跑通生产级构建

## 四、技术难点攻关

### 难点 1：Spring Boot 4 / JDK 25 生态适配（影响面最大）

新版本组合下多个 starter / 工具链断档，逐一攻坚：

| 问题                  | 现象                                     | 解法                                                |
| --------------------- | ---------------------------------------- | --------------------------------------------------- |
| Druid 不兼容          | druid-spring-boot-3-starter 自动装配失效 | 引核心包 + 手动注册 DataSource                      |
| MyBatis-Plus 分页失效 | Boot 4 下 jsqlparser 解析异常            | 单独引入 mybatis-plus-jsqlparser                    |
| Lombok 失效           | JDK 25 注解处理器不生效                  | 显式配置 annotationProcessorPaths                   |
| 网关路由不生效        | 配置键迁移                               | 迁移至 `spring.cloud.gateway.server.webflux.routes` |

### 难点 2：SkyWalking 在 Spring Framework 7 下插件失活

spring-mvc / webflux / gateway 插件的 witness 类检测失效，入口 Span 命名降级、链路入口不可见。

- 攻关：定位到 Tomcat 插件可接管入口 Span，URL 命名虽有降级但 sw8 传播与跨服务链路完全正常
- 结论：拓扑、Trace、SQL、错误追踪四项能力实测全部可用

### 难点 3：秒杀缓存的三个边界场景

1. **预热空窗**：定时任务 1 分钟间隔存在键尚未写入的窗口 → 下单时发现键缺失即回源 DB 并 setnx 回写后重试，兼具防缓存击穿
2. **预热不覆盖**：若直接 set 会把已扣减的库存改回原值（超卖）→ 全程 setnx，进行中的活动键不被预热任务覆盖
3. **消费失败不无限重试**：MQ 消费异常若重回队列会形成毒丸 → 补偿（Redis 库存 +1、删防重键）后 ack，损失一次请求但不阻塞队列

### 难点 4：登出黑名单的「误杀」问题

朴素方案按 userId 判断黑名单会把用户重新登录的新 token 一并拦下。改为黑名单 value 存被注销的 token 原文、网关**全文精确比对**，登出旧 token 与新登录互不影响。

### 难点 5：分布式锁的正确使用

- 锁粒度选择：防重复下单按**会员维度**（`lock:order:{memberId}`）加锁，不同用户互不阻塞
- 锁释放安全：finally 中先判断 `isHeldByCurrentThread()` 再 unlock，避免业务超时后释放他人锁
- 锁参数权衡：等待 10s（用户体验）+ 租期 30s（业务最长耗时），未获锁直接返回「系统繁忙」

## 五、已知局限与演进方向

诚实记录当前边界，作为后续迭代依据：

1. **秒杀成交价未启用**：秒杀订单落库取商品原价，`seckillPrice` 字段尚未参与计价——展示价与成交价一致性待补齐
2. **异步扣库存缺补偿闭环**：普通订单 MQ 消费者扣库存失败仅记录错误日志，未回滚订单——可引入本地消息表 / 定时对账兜底
3. **秒杀库存以 Redis 为准**：秒杀链路不扣 DB 库存（性能取舍），Redis 数据丢失依赖回源机制，极端场景下「进行中活动」的已扣减量不可恢复
4. **前端包体积**：owner-web 主包 1.2MB（Element Plus 全量引入），可做按需引入优化
5. **管理端功能深度**：数据请求已打通，导出、批量操作、报表等运营功能可继续完善
